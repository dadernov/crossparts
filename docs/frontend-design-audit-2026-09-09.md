# Аудит фронтенда и дизайна CrossParts

Дата: 2026-09-09. Проверяемый код: `85bf044`.

## Вывод

Интерфейс имеет хорошую основу для B2B-инструмента: понятное разделение одиночного
и пакетного поиска, спокойные цвета, единые карточки, простой вход. Главная проблема
сейчас — достоверность состояния поиска и задания. Пользователь не видит разницы
между отсутствием аналогов и недоступностью источников, а также не может оценить
полноту результата. Следующий этап лучше начать с этих сценариев и безопасности
вывода данных, затем улучшить таблицы, мобильное представление и визуальные детали.

## Метод и границы проверки

- Прочитаны оба HTML-шаблона, весь JavaScript и CSS, связанные API, авторизация,
  обработчик заданий, агрегатор, Excel-импорт/экспорт и реестр каталогов.
- Реальные шаблоны Jinja и статические файлы открыты в Chromium через Playwright.
  Ответы API подменены контролируемыми примерами на локальном адресе `audit.local`.
  Это проверка интерфейса, а не подтверждение работы внешних каталогов.
- Проверены ширины 320, 375, 390, 768 и 1440 px, вход, история с ошибкой задания,
  ответ заблокированного каталога и обработка недоверенных строк.
- Визуально просмотрены desktop, mobile и login. Скриншоты находятся локально
  в `out/audit-desktop.png`, `out/audit-mobile.png`, `out/audit-login.png`;
  `out/` исключён из Git.
- Проверены пограничные сценарии Excel в памяти. Основной набор: 71 passed,
  10 skipped. Проверка `git diff --check` успешна.
- Не выполнялись реальные загрузки заданий, подбор пароля, изменение production-БД,
  проверки внешних каталогов, Safari/Firefox, реальные мобильные устройства,
  screen reader, Lighthouse или полный автоматический WCAG-аудит. Метрики
  производительности и соответствие WCAG не заявляются.

Приоритеты: P0 — безопасность/неверный результат, P1 — основной сценарий и доступность,
P2 — удобство и поддерживаемость. «Код» означает вывод из реализации;
«воспроизведено» — отдельную выполненную проверку.

## Дизайн и доступность

Сильные стороны: спокойная синяя палитра подходит рабочему сервису, контрастные
карточки выделяют действия, иерархия H1/H2 последовательна, основная кнопка поиска
хорошо заметна. Страница входа визуально согласована с основным экраном; у её полей
есть labels, required и autocomplete. Общий `lang=ru` и `aria-live` одиночного
поиска уже присутствуют. Нативный focus-outline не отключён.

Рекомендуемые изменения:

1. **Рабочая площадь.** Высокий рекламный hero занимает значительную часть первого
   экрана, особенно на телефоне. После входа сделать компактную шапку с названием,
   аккаунтом и коротким пояснением. Основное пространство отдать вводу и результатам.
2. **Типографика.** Исправить невалидные правила font, закрепить шкалу размеров.
   Мелкие прописные заголовки 11px и пояснения 13px использовать ограниченно.
   Inter указан, но не подключён: сознательно выбрать системный стек либо поставить
   локальный шрифт. Внешний шрифт не является обязательным улучшением.
3. **Единые состояния.** Добавить hover, focus-visible, disabled, busy, error,
   success для компонентов. На мобильном согласовать ширину кнопок загрузки:
   сейчас они имеют разную ширину. Проверить контраст каждого состояния измерением;
   в этом аудите соответствие цветовых пар WCAG не измерялось.
4. **Доступные уведомления.** У upload и history нет live-region; прогресс нарисован
   div/i без семантики progressbar. Добавить статусные объявления без повторного
   чтения всей таблицы каждые 5 секунд. Дать ошибкам связь с полями, таблицам —
   понятные названия, заголовкам столбцов — scope.
5. **Мобильный вход и фокус.** Проверить длинный логин, длинное имя файла, увеличение
   текста 200%, 320px и клавиатуру устройства. Autofocus OE может неудобно открывать
   экранную клавиатуру; это требует проверки на настоящем телефоне. В карточках
   использовать min-width:0 у гибких полей вместо жёсткого минимума 280px.
6. **Экран входа.** Добавить показ пароля и понятный путь получения/восстановления
   доступа (хотя бы контакт администратора). Сохранять логин при ошибке, обозначать
   ошибку доступно. Не обещать self-service восстановление без backend.
7. **Масштабирование таблиц.** Для desktop важнее видимость источников, фильтры и
   закреплённые заголовки, чем дополнительные декоративные элементы. Для mobile —
   карточки истории и действие скачивания без горизонтальной прокрутки.

## Сопутствующие замечания по границе UI/API

- `app/session.py` не задаёт cookie `Secure` и серверный срок действия подписи.
  `app/config.py` содержит публичное значение session_secret по умолчанию и
  начальную пару admin/changeme. Это риск при развёртывании с умолчаниями;
  фактические production-секреты в этом аудите не проверялись.
- `init_db` создаёт аккаунт только если его ещё нет. Простая смена CP_USERS не
  обновляет пароль существующего аккаунта; нужна явная процедура смены.
- В API при пустом CP_API_KEYS сохраняется анонимный tenant default. Формулировка
  «всё защищено входом» должна учитывать эту настройку и модель доступа API.
- `.env.example` и отдельные разделы README отстают от нового входа и списка
  источников. В отчёте нельзя считать старые утверждения о публичном демо
  подтверждением текущей конфигурации.
- JS/CSS/HTML сжаты прямо в исходниках, без отдельного процесса сборки. Разбить
  JS на читаемые функции по сценариям, форматировать CSS и шаблоны. Переход на React
  ради этого объёма сам по себе не требуется.
- Имеющиеся тесты проверяют Python, но не покрывают UI-состояния, новую сессию,
  браузерный вход и race conditions. Успешные 71 тест не опровергают дефекты выше.

## Порядок реализации и приёмка

1. **Безопасный и достоверный результат:** F01–F05, F12. Приёмка: недоверенный текст
   не исполняется; заполненный шаблон не теряет строки; блокировка, пустой ответ,
   частичный результат и упавшее задание визуально различаются.
2. **Надёжные действия:** F06–F10. Приёмка: двойной клик не создаёт два задания,
   старый ответ не заменяет новый, сеть/429/422 имеют понятные сообщения,
   поля именованы и доступны с клавиатуры.
3. **Работа с данными:** источники, детали заданий, копирование и фильтр,
   кэш-метаданные, аккуратный polling. Приёмка на 0/1/500 результатах,
   длинных именах и нескольких одновременно обрабатываемых заданиях.
4. **Визуальная доводка:** компактная шапка, единая типографика и компоненты,
   мобильная история, вход. Приёмка на 320/375/768/1440px и при увеличении текста,
   затем Safari/Firefox, реальное мобильное устройство и screen reader.

Текущий аудит фиксирует существующую реализацию и план улучшений. Исправления
функциональности и редизайн в рамках этого коммита не вносились.
