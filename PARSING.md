# Как CrossParts парсит каталоги и как безопасно расширять покрытие

Подготовлено 22 сентября 2026 года по локальному коду на коммите `ecf02f1` и файлу **«Ресурсы для парсинга.xlsx»**.

**Это объяснение и план. Парсеры, настройки, рабочая база и production не изменялись. Живые каталоги и тесты в рамках подготовки документа не запускались.** Описанные ниже проверки и подключения предстоит реализовать отдельно.

Документы для продолжения работы:

- [Машиночитаемый план](plans/catalogue-expansion.yaml): этапы, тестовые сценарии, критерии качества и скорости, выпуск и откат.
- [Построчная сверка Excel](plans/catalogue-resource-inventory.yaml): исходные значения, номера строк, источники, группы, существующий код и пробелы в покрытии.

## Что оказалось в Excel

В файле **47 записей в четырёх разделах, 33 бренда и 36 различных URL**. Получается **34 логических источника**: для NiBK указаны два разных сайта. Повтор одного сайта в разных разделах не означает необходимость писать несколько парсеров.

| Раздел Excel | Строк с ресурсами | Группы сервиса |
|---|---:|---|
| Диски и колодки | 17 | `brake_discs`, `brake_pads` |
| Амортизаторы | 14 | `shock_absorbers` |
| Радиаторы охлаждения | 7 | `radiators` |

В коде зарегистрировано **13 адаптеров**. Из них **11 включены в настройках по умолчанию исходного кода**, а `jnbk` и `mintex` не включены. Это не проверка фактической production-конфигурации и не утверждение, что все эти сайты сейчас отвечают.

Для **21 источника адаптера пока нет**. Часть из них уже упомянута в `catalog.json`, но запись в справочнике не выполняет поиск.

Обнаружены расхождения:

- В справочнике отсутствуют Marshall, Metaco, Masterkit, LYNX Auto, GANZ, Monroe, Febest и TORR.
- SAKURA ошибочно записана как `SALURA`/`salura`; данные фактически идут через адаптер Brixo.
- Для TRW в справочнике указаны только шланги, хотя Excel также требует диски/колодки и амортизаторы. У ATE не указаны шланги.
- MONAER в Excel ведёт на конкретную карточку товара, HEL — на страницу «О нас», некоторые другие ссылки — на страницы брендов. Это исходные адреса для исследования, а не готовые адреса поиска.
- Старые пометки о блокировке, B2B-входе, 404/503 и отсутствии обратного поиска нужно перепроверить. Они прочитаны из кода, а не установлены свежим сетевым тестом.

Сам файл **«Ресурсы для парсинга.xlsx» — список сайтов для разработки**. Его не нужно загружать в форму поиска как Excel с артикулами: это другой формат и другое назначение.

## Как поиск работает сейчас

### 1. Получаем номер и выбираем каталоги

Запрос приходит из поля поиска или из строки загруженного Excel. Проверяются доступ и квота. Для Excel создаётся задание; для одиночного запроса результат также сохраняется в историю.

Модуль [app/excel.py](app/excel.py) читает первый лист, распознаёт колонки с номером, артикулом заказчика, товарной группой и названием детали. Он ищет заголовки среди первых 30 строк. Для обычных листов первая пустая строка после начала данных завершает чтение; для собственного листа-шаблона «Загрузить этот лист» пропуски разрешены. Это существующее поведение, которое нужно сохранить тестами или менять отдельно и осознанно.

[app/sources/registry.py](app/sources/registry.py) выбирает включённые источники с учётом группы. Например, при группе «Радиаторы» незачем обращаться к каталогу, заявленному только для колодок.

Важная тонкость: **это отбор источников, а не универсальная проверка каждой найденной детали**. Сейчас `source.lookup()` получает номер, но не группу. Если сайт возвращает смешанный ассортимент, адаптер должен сам уметь отличать подходящие позиции; одной настройки `groups` недостаточно.

Без группы выбираются все источники из настроек по умолчанию. Поэтому при расширении списка особенно важно проверить запросы с неизвестной группой: количество внешних обращений может заметно вырасти.

### 2. Проверяем кэш

[app/aggregator.py](app/aggregator.py) ищет ранее полученный ответ по паре:

```text
источник + нормализованный номер
```

Например, `58101-H5A25` и `58101H5A25` имеют одинаковый ключ. Нормализация приводит латинские буквы к верхнему регистру и удаляет символы вне `A–Z` и `0–9`. Это техническое сравнение строк, а не проверка взаимозаменяемости деталей.

При свежем кэше сайт повторно не запрашивается. В коде срок хранения по умолчанию — **168 часов**. Кэшируются найденные и отрицательные ответы; ошибки и блокировки — нет.

Сейчас ключ не содержит версию парсера и группу. Поэтому нельзя просто заменить логику нового адаптера и считать старые ответы правильными: в плане предусмотрены проверка совместимости и адресное обновление кэша. Также надо проверить конкурентные запросы одного номера: текущий код не гарантирует один общий внешний запрос на все одновременные промахи кэша.

### 3. Адаптер обращается к конкретному сайту

У каждого каталога свой способ поиска. **Мы не используем один универсальный парсер всех страниц и не просим ИИ угадывать аналоги.** Адаптер воспроизводит запрос поиска и читает конкретные структурированные данные сайта.

Основные способы:

| Способ | Что делает код | Примеры |
|---|---|---|
| JSON API | Отправляет номер, читает поля ответа и карточки | KYB, Brixo, NiBK через Brixo |
| HTTP + HTML | Получает поисковую выдачу, открывает найденные карточки, разбирает таблицу OE/кроссов | SB NAGAMOCHI, TRIALLI, LUZAR, HOLA, BRANNOR, HEL |
| Форма с сессией | Получает cookies/служебные поля, отправляет форму, читает карточки | Brembo, Nissens, JNBK, Mintex |
| Браузер | Открывает страницу Chromium и читает DOM, когда без JavaScript нельзя | Поддерживается инфраструктурой; `profiles.json` сейчас пуст. У Mintex есть браузерный fallback |

Примеры из действующего кода:

- **Brixo:** поиск `/api/sku/search`, затем `/api/sku/info/<артикул>`. В `references` лежат пары производителя и номера. Адаптер NiBK использует этот же транспорт и отбирает товары NiBK. Два адаптера не означают два независимых первоисточника.
- **KYB:** POST `/api/2/cross`. Из ответа читаются собственный артикул KYB, оригинальный номер и автопроизводитель. Номер перед отправкой очищается от разделителей.
- **Brembo:** сначала cookies и antiforgery-токен, затем поиск кода и две таблицы: оригинальные номера и номера других производителей запчастей.
- **SB NAGAMOCHI:** AJAX-поиск возвращает HTML карточек внутри JSON; затем читается таблица аналогов на карточке.
- **TRIALLI:** обычный поиск и блоки «ОЕМ-номер» на товарной странице.
- **Nissens:** форма поиска, выбор прямых совпадений, запрос подробностей. Другую деталь для того же автомобиля нельзя добавлять как аналог.

Это описание реализации, **не гарантия, что внешние endpoints не изменились**. Перед подключением или выпуском их проверяют отдельно.

### 4. Собираем подтверждённые пары

Внутренний объект кросса содержит:

```text
бренд, номер, тип номера, источник, артикул карточки, URL
```

Собственный артикул найденного товара тоже может быть результатом. OE-номера и аналоги извлекаются из таблиц каталога. Наличие числа в названии, цене, характеристике или списке подходящих автомобилей не делает это число кроссом.

**OEM — не марка.** В некоторых источниках конкретный производитель не указан, и текущий код использует `OEM` как техническую метку. Нельзя по этой метке выдумывать LADA, Renault или другой бренд. Кроме того, текущая классификация неизвестного бренда как OEM — эвристика, не доказательство. В плане это отдельная проверка точности.

Связь в каталоге также не заменяет проверку применимости: комплекты, стороны, оси и варианты исполнения могут отличаться. Поэтому эталон должен подтверждать не только текст номера, но и контекст связи.

### 5. Объединяем ответы

Каталоги для одного номера запрашиваются параллельно. Совпавшие пары **«бренд + нормализованный номер»** объединяются; список источников и исходных товаров сохраняется. Одинаковые номера у разных брендов остаются отдельными парами.

Глобального справочника, который надёжно объединяет все варианты названий производителей, в этом механизме нет. `VW` и `VOLKSWAGEN` нельзя считать уже полностью решённым случаем. Объединение псевдонимов требует проверенного словаря и тестов; например, BILSTEIN и FEBI BILSTEIN автоматически объединять нельзя.

Сейчас при объединении сохраняется первый URL пары, а не все ссылки доказательства. Исходный искомый номер не удаляется: он перемещается в конец. Это реальные особенности текущей реализации, а не предложения нового поведения.

### 6. Сохраняем результат и выгружаем Excel

[app/jobs.py](app/jobs.py) ведёт задания и прогресс. Внутри одного Excel номера сейчас обрабатываются последовательно, а каталоги для каждого номера — параллельно. Значения по умолчанию исходного кода: четыре обработчика заданий и до двух одновременных вызовов одного адаптера.

История и экспорт используют сохранённые результаты. Выгрузка содержит два представления: отдельные кроссы строками и сгруппированные номера. При расширении каталогов нельзя потерять артикул заказчика, принадлежность строки запросу, источник, квоту или изоляцию истории между клиентами.

Статус задания `done` означает, что обработка закончилась. Он **не гарантирует**, что все внешние сайты ответили и все их карточки прочитаны. Поэтому проверки полноты должны смотреть на результаты каждого источника, а не только на зелёный статус задания.

### Дополнительный поиск через найденные кроссы

В коде есть опциональный второй проход: взять прямые найденные номера и попробовать их в каталогах, которые вернули `not_found`. По умолчанию в исходном коде он **выключен**.

Предусмотрены ограничения: общий бюджет шесть дополнительных вызовов, до двух кандидатов на источник и двадцать секунд на второй проход. Рекурсивного бесконечного обхода нет. Источники с ошибкой или блокировкой повторно этим механизмом не опрашиваются.

Это потенциальное расширение выдачи, но косвенная связь не равна доказанной прямой взаимозаменяемости. Во время подключения новых каталогов нельзя заодно незаметно включать этот режим: нужна отдельная проверка цепочек, ложных совпадений, времени и происхождения результата.

## Что именно будем проверять

### На каждом каталоге

Нужны и тесты чистого парсинга сохранённой HTML/JSON-разметки, и тест полного HTTP-сценария: правильные параметры, cookies, токены, карточки, пагинация, обработка ошибок. Первый вид ловит ошибки разбора; второй — ситуации, когда парсер правильный, но до него не доходит нужная страница.

В плане заданы 30 общих классов проверок адаптера и отдельные особенности для **всех 34 источников**. Дополнительно расписаны нормализация, кэш, объединение, маршрутизация, Excel, история, доступ, экспорт и конкурентная работа.

Для каждой пары **«источник — группа»** предлагается собрать минимум:

- 12 разных подтверждённых положительных запросов;
- 4 подтверждённых отрицательных;
- 4 неоднозначных или частичных случая.

Для 64 пар из Excel это **1280 эталонных сценариев**, когда источники будут исследованы. Плюс регрессия текущих групп, которых нет в соответствующих разделах Excel: например, шланги SB и несколько групп HOLA. Это целевой объём будущей матрицы, а не число уже написанных тестов. Если каталог недоступен, эталоны не выдумываем и источник не выпускаем.

Ожидаемые результаты размечаются по первичным данным каталога, независимо от нашего алгоритма. Сохранённый кэш не подходит на роль доказательства собственной правильности. Проверяется точное множество пар, включая **запрещённые ложные совпадения**, а не условие «нашлось хоть что-то».

Особенно важные случаи:

- Сайт отдаёт одну общую выдачу на любой номер.
- Нужна авторизация, пришла защита или изменилась разметка, а программа ошибочно пишет «не найдено».
- Первая карточка правильная, остальные не загрузились, но результат выглядит полным.
- В ответ попала другая деталь для той же машины.
- Собственный артикул, OE, стандарт WVA/FMSI и номер комплекта перепутаны.
- Один номер одновременно запрашивают несколько пользователей.
- Общий backend обслуживает несколько брендов, и нагрузка случайно удваивается.

### На всём сервисе

Проверяем путь от поля/Excel до истории и скачанного файла. В том числе сохранение порядка и SKU, квоты, явное включение trial, чужие задания, обновление страницы, ошибки внешних сайтов, прерванное соединение, перезапуск worker и повторную обработку очереди.

Любое изменение общего кода — нормализации, registry, кэша, aggregator, импорта/экспорта — требует регрессии **всех существующих адаптеров**, даже если новая работа касается одного бренда.

### На скорость

Раздельно измеряем время ожидания очереди, внешнего запроса, разбора, кэша, объединения и Excel. Сравниваем холодный и прогретый кэш, одиночный запрос и пакеты 10/100/1000 строк, разные уровни параллельности. Проверяем p50/p95/p99, память, количество HTTP-вызовов и закрытие браузерных контекстов.

**Большая нагрузка идёт только на локальные имитаторы каталогов.** Реальным сайтам — небольшие дозированные пробы с ограничением частоты и остановкой при 429/блокировке. Малую сетевую выборку нельзя выдавать за надёжное измерение p99.

В плане предложены начальные бюджеты: не более 10% ухудшения p95 существующего поиска на сопоставимом стенде, целевой p95 кэшированного ответа до 500 мс и раздельные бюджеты HTTP/браузерных источников. Эти числа **ещё не измерены**; их фиксируют после baseline на staging до сравнения нового варианта. Быстрый неправильный ответ не считается улучшением.

## Порядок подключения

1. **Подготовка:** изолированные тесты, эталоны существующих адаптеров, baseline скорости, воспроизведение рисков кэша/очереди, необходимые защитные механизмы.
2. **Диски и колодки:** исследование источников из первого раздела; первым — один источник с подтверждённым обратным поиском. Колодки и диски проходят допуск отдельно.
3. **Амортизаторы:** подтверждённые расширения общих адаптеров, затем новые каталоги по одному.
4. **Радиаторы:** LUZAR/Nissens/Brixo как регрессия, новые источники по одному; NRF/AVA сначала проверяются на доступность и пригодность.
5. **Шланги:** отдельные эталоны и допуск каждого источника, включая уже известные общие каталоги.
6. **Итоговая сверка:** у каждой из 47 строк есть результат — подключено с доказательствами либо отложено с конкретной причиной.

Недоступный каталог не блокирует исследование остальных. Он остаётся выключенным, с понятной зависимостью: доступ, API, выгрузка производителя или отсутствие подтверждённого обратного поиска. «Раздел завершён» не означает, что все его сайты обязаны быть подключены любой ценой.

Один выпуск — **один источник и одна группа**. Если общий адаптер начал поддерживать новую категорию, это не разрешает автоматически включать все остальные.

## Как не повредить production

До реализации следующего этапа остаёмся в документах. При будущей работе:

- Отдельный checkout, процесс, порт, база, кэш, файлы и сессии. Тесты не импортируют приложение с production-настройками и не используют клиентские квоты.
- Offline-тестам сеть запрещена. Есть отдельный контролируемый live-режим. В текущих тестах даже `CP_LIVE=0` — непустое значение и включает live-проверки, поэтому одной такой переменной недостаточно для изоляции.
- Новый источник выключен, пока не прошёл тесты, live-проверку, staging и проверку отката. Ограничение должно действовать и при явном указании source key в API.
- Нельзя запускать staging/второй worker с рабочей базой: при старте `JobRunner` подхватывает незавершённые задания. Это риск повторной обработки клиентского Excel.
- До согласованного выпуска готовится консистентный backup SQLite и проверяется восстановление на стенде. Копии одного `.db` при активном WAL недостаточно как процедуры резервирования.
- Перезапуск требует проверенного завершения/передачи очереди. Текущая архитектура сама по себе не даёт основания обещать бесшовный zero-downtime rollout. Если безопасный способ ещё не готов, выпуск откладывается.
- Сначала выделенная тестовая группа пользователей, затем расширение после отчёта. Любой ложный кросс, лишнее списание, утечка или потеря задания — немедленное отключение нового источника.
- Откат касается кода, включения источника и его несовместимого кэша. **Рабочую клиентскую базу нельзя откатить назад вместе с новыми поисками и историей.**

Для решения о выпуске нужен конкретный отчёт: что подключается, точные результаты тестов, сравнение качества/скорости, ограничения, оставшиеся блокеры и проверенный способ отката. Текущее поручение такой выпуск не разрешает.
